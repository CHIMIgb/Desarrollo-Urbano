P39: 2. Decisiones Arquitectonicas Clave
P40: 2.1 Motor 3D: Deck.gl + MapLibre (no Three.js puro)
P41: Para un sistema con datos GIS reales y visualizacion de objetos 3D sobre mapa, Deck.gl combinado con MapLibre GL JS es la arquitectura correcta por las siguientes razones:
P43: Deck.gl fue disenado especificamente para visualizacion geoespacial masiva via WebGL
P44: Maneja millones de puntos y poligonos nativamente sin degradacion de rendimiento
P45: ScenegraphLayer permite renderizar modelos GLTF 3D con posicionamiento geografico real
P46: MapLibre gestiona la proyeccion geografica y el terreno 3D con tiles Terrain-RGB
P47: Three.js puro requeriria implementar todo el sistema de proyeccion geografica desde cero
P49: Three.js se usa complementariamente para el editor de objetos custom y manipulacion de geometrias cuando se necesita mas control del que ofrece Deck.gl.
P51: IMPORTANTE: Deck.gl y MapLibre comparten el canvas WebGL mediante el componente DeckGL de React con MapLibre como prop 'map'. Nunca deben instanciarse como dos instancias independientes ya que generan
P53: 2.2 Base de Datos: PostgreSQL + PostGIS (obligatorio)
P54: PostGIS es la extension que convierte PostgreSQL en una base de datos geoespacial. Es el estandar de facto para datos GIS y es no-negociable por las siguientes razones:
P56: Almacena geometrias nativas (puntos, lineas, poligonos) en formato optimizado
P57: Permite queries espaciales nativas: '¿que edificios estan dentro de este radio?'
P58: Calcula areas, intersecciones, distancias directamente en la base de datos
P59: Compatible con estandares GIS: GeoJSON, WKT, WKB, GML
P60: Exportacion futura a CityGML para v2 (estandar internacional de modelos urbanos 3D)
P62: Guardar geometrias como JSON plano en PostgreSQL sin PostGIS es un error de arquitectura que genera deuda tecnica severa.
P64: 2.3 Backend: FastAPI (Python)
P65: Python es la eleccion correcta para el backend porque todo el ecosistema GIS es nativo en Python: GDAL, Shapely, Fiona, PyProj, Rasterio. FastAPI permite exponer operaciones GIS como API REST de forma
P67: 2.4 Fuentes de Datos GIS (Open Source / Open Data)
P68: OpenStreetMap via Overpass API: datos de calles, edificios y parques existentes (gratuito)
P69: Terrain-RGB tiles (AWS Open Data): elevacion real del terreno en todo el mundo (gratuito)
P70: Overture Maps Buildings: footprints 3D de edificios reales de ciudades globales (2023, open data)
P71: INEGI - Continuo de Elevaciones Mexicano: datos de elevacion para Mexico (open data oficial)
P72: Nominatim (OSM): geocodificador open source para busqueda de ubicaciones (gratuito)

P96: 4. Modelo de Datos
P97: Cada proyecto urbano es un conjunto de capas GIS sobre un area geografica real. La estructura refleja el estandar GeoJSON Feature Collection, compatible con herramientas GIS externas.
P100: 4.1 Estructura de Properties (JSONB)
P101: El campo properties en Feature es JSONB (JSON binario indexable en PostgreSQL). Esto permite flexibilidad total por tipo de objeto sin requerir migraciones de esquema. Ejemplos de propiedades por tipo
P103: Edificio: { height: 45, floors: 12, name: 'Torre Central', uso_suelo: 'comercial', area_m2: 850 }
P104: Casa: { floors: 2, name: 'Casa tipo A', area_m2: 120, fraccionamiento: 'Las Palmas' }
P105: Carretera: { type: 'primaria', lanes: 4, name: 'Blvd. Insurgentes', length_m: 2400 }
P106: Parque: { name: 'Parque Central', area_m2: 5000, amenities: ['canchas', 'juegos'] }
P107: Alumbrado: { type: 'LED', height_m: 8, spacing_m: 30 }
P109: 4.2 Relaciones de Datos
P110: Un Project tiene muchos Layers (1:N)
P111: Un Layer tiene muchas Features (1:N)
P112: Cada Feature tiene exactamente un registro de geometria PostGIS
P113: El terrain data se cachea por bbox del proyecto para evitar requests repetidos a los tile servers
P116: 5. Flujo del Editor 3D
P117: El editor es la pieza central del MVP. El flujo de interaccion del usuario es el siguiente:
P119: 5.1 Flujo Principal de Edicion
P120: Usuario selecciona un tipo de objeto en la paleta lateral (ej: Edificio)
P121: El mapa entra en modo 'colocacion': el cursor cambia y aparece un preview del objeto
P122: Usuario hace click en el punto del mapa donde desea colocar el objeto
P123: El sistema calcula las coordenadas geograficas reales del punto clickeado
P124: Se genera un GeoJSON Feature con las coordenadas y propiedades default del tipo
P125: Deck.gl renderiza el objeto 3D (modelo GLTF) en esa posicion del mapa
P126: Se abre el panel de propiedades para que el usuario configure altura, nombre, etc.
P127: El auto-save envia un POST/PATCH a la API de FastAPI con el Feature actualizado
P128: La API persiste la geometria en PostGIS y las propiedades en la columna JSONB
P130: 5.2 Operaciones de Edicion
P131: Seleccion: click en objeto existente → resalta y abre panel de propiedades
P132: Movimiento: drag del objeto a nueva posicion → actualiza coordenadas en DB
P133: Redimensionar: handles en los vertices del objeto → actualiza geometria
P134: Borrar: tecla Delete o boton en panel → soft delete con flag 'deleted_at'
P135: Undo/Redo: Zustand + Immer mantienen historial de estados, Ctrl+Z / Ctrl+Y
P136: Trazado de carreteras: click secuencial de puntos, doble-click para terminar polyline
P137: Zonas (parques, fraccionamientos): poligono con click secuencial, cierre automatico

P179: 8. Consideraciones Tecnicas Criticas
P180: 8.1 Rendimiento WebGL
P181: El cuello de botella principal del sistema es el rendimiento del canvas WebGL compartido entre Deck.gl y MapLibre. Para mantener 60 fps con muchos objetos 3D se deben aplicar las siguientes estrategia
P182: Level of Detail (LOD): reducir complejidad de modelos a mayor distancia de camara
P183: Frustum culling: no renderizar objetos fuera del viewport de la camara
P184: Instanced rendering: renderizar multiples copias del mismo modelo en una sola llamada GPU
P185: Tile-based loading: cargar datos GIS solo para el area visible (bbox del viewport)
P186: Web Workers: procesamiento de datos GIS en hilos separados para no bloquear el render
P188: 8.2 Seguridad
P189: Todas las rutas de la API de FastAPI protegidas con validacion JWT
P190: Row Level Security (RLS) en PostgreSQL: usuarios solo acceden a sus propios proyectos
P191: Validacion de geometrias en el backend: prevenir inyeccion de geometrias maliciosas
P192: Rate limiting en la API para prevenir abuso (especialmente en queries a Overpass API)
P193: CORS configurado estrictamente para permitir solo el dominio del frontend
P195: 8.3 Offline y PWA
P196: La estrategia de cache del service worker debe ser diferenciada por tipo de recurso:
P197: Shell de la aplicacion (HTML, CSS, JS): cache-first, actualiza en background
P198: Modelos GLTF de objetos: cache permanente (no cambian entre versiones del MVP)
P199: Tiles del mapa base: network-first con fallback a cache (cambian con actualizaciones OSM)
P200: Datos de proyectos del usuario: solo lectura offline, las escrituras requieren conexion
P202: 8.4 Accesibilidad y UX
